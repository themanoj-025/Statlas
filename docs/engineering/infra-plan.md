# Statlas — Infrastructure Plan (staging + backups + secrets)

**Date:** 2026-08-14 · **Closeout C5** · Status: **planned, not yet built**
(these are production-hosting concerns; this document makes them explicit so
they are never silently absent).

## 1. Staging environment plan

The production stack is defined and proven locally (`docker-compose.yml`:
PostgreSQL 16 + FastAPI + Next.js standalone). Before real traffic lands:

1. **A staging host** — same Compose stack, own volume, seeded with the
   `fixture-demo` dataset first, then a real production scrape (Part A gate)
   once `STATLAS_DATASET_MODE=production` is validated. Staging and production
   are **separate deployments** — never a shared database.
2. **Domain + TLS** — statlas.com (or chosen domain) with a managed TLS
   certificate; staging on `staging.statlas.com`. `STATLAS_PUBLIC_API_URL` and
   the CORS `allow_origins` list in `app/api/main.py` are updated per
   environment (currently only localhost origins are allowed).
3. **Secrets management** — environment variables (Postgres credentials,
   `API_FOOTBALL_KEY`, dataset mode) via the host's secret store; never
   committed (`.gitignore` already excludes `.env.*`; `.env.example` documents
   keys without values). CI secret scanning (gitleaks) prevents accidental
   commits (see §3).
4. **CI gate before staging deploy** — every push to `main` runs pytest, ruff
   (incl. DTZ), typecheck, production build, and (Part B) Lighthouse + axe +
   e2e checks. A deploy to staging is a tagged manual action, never
   automatic-on-push.
5. **Observability** — pipeline logs to stdout (already structured via
   `logging`); add a log aggregator before launch. The weekly-refresh job
   emits a `RefreshReport` (errors list) — surface failures to an alerting
   channel when the job runs unattended in production.

## 2. Database backup strategy

1. **PostgreSQL** (`pg_dump` logical backups):
   - **Daily** full dump to object storage (e.g. S3-compatible bucket),
     retained 30 days.
   - **Weekly** dump additionally copied off-site (different region/provider)
     as the recovery point for the "everything is gone" scenario.
   - Dumps are encrypted at rest (bucket-side encryption); credentials for the
     bucket live in the host secret store.
2. **Why logical dumps over volume snapshots** — the data is small (tens of
   thousands of rows even after a full season) and the schema is versioned by
   `schema.sql` + `scripts/migrations/`, so a logical dump is portable across
   Postgres minor versions and restores cleanly. Volume snapshots are a
   faster complement, not a replacement.
3. **Restore drill** — before launch, run one documented restore into a throwaway
   container and verify the API serves data from the restored DB (the
   postgres-parity-notes.md procedure is the same shape).
4. **SQLite dev** — `data/` is gitignored and regenerated by
   `scripts/seed_dev_db.py`; no backup needed (rebuildable by design).

## 3. Dependency + secret scanning in CI (implemented)

- **Dependabot** (`dependabot.yml`) — weekly updates for Python
  (`requirements.txt`) and npm (`web/package.json`), with a daily version-updates
  job for the lockfile.
- **`pip-audit`** — Python dependency vulnerability scan, enforced (fails the
  job on any known vulnerability; `--fix` is run manually, not in CI).
- **`npm audit`** — web dependency scan with `--audit-level=high`, enforced.
- **gitleaks** — secret scanning on every push/PR; a found secret blocks merge.

## 4. Out of scope for this closeout (tracked)

- The staging host, TLS, log aggregation, and backups are **planned but not
  provisioned** — they require hosting credentials a founder must provide.
  They are tracked in `docs/legal/pre-launch-human-actions.md` as launch
